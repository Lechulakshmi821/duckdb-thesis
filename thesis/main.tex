\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}
Modern analytical workflows increasingly combine relational data processing
with machine learning, yet the two are typically kept separate: data is
extracted from the database, gradients are computed in an external
framework, and results are written back. This causes unnecessary data
movement and prevents the database from optimizing the combined workload.
Automatic differentiation (AD), the technique underlying gradient-based
machine learning, is not natively supported by relational database systems.

This thesis integrates AD directly into DuckDB using higher-order SQL
lambda expressions as differentiable programs: a lambda passed to an AD
function is compiled into an internal representation from which gradients
are computed automatically. Both forward-mode and reverse-mode AD are
implemented, each compiled once at bind time into a flat instruction tape,
optimized through common subexpression elimination and tiled vectorisation,
and finally JIT-compiled to native machine code via LLVM. The implementation
is further extended so that lambda expressions can be stored as first-class
typed values in table columns, with both a bind-time path retaining the
full optimization pipeline and a dynamic per-row path for lambdas that vary
across rows.

Evaluated on linear regression gradient-descent workloads from one thousand
to fifty thousand tuples, both forward-mode and reverse-mode AD match the
handwritten SQL baseline at $1.00\times$ overhead at fifty thousand tuples
after all optimizations; the stored-lambda bind-time path matches this same
baseline, while the dynamic path shows the expected overhead from operating
without JIT compilation. The thesis demonstrates that differentiable
computation can be expressed and executed directly inside SQL queries with
performance equivalent to handwritten SQL gradients.

\chapter{Introduction}
\label{ch:introduction}

\section{Background and Motivation}

The interaction between database systems and machine learning workflows has
grown substantially in recent years. Relational database management systems
(RDBMS) have long provided efficient mechanisms for structured data storage and
querying~\cite{codd1970relational,selinger1979access}, while modern machine
learning frameworks---such as TensorFlow~\cite{abadi2016tensorflow},
PyTorch~\cite{paszke2019pytorch}, JAX~\cite{jax2018}, and
MXNet~\cite{chen2015mxnet}---excel at gradient-based optimization and numerical
computation.

In real-world analytical pipelines these two worlds remain largely separate. A
typical workflow extracts data from the database, loads it into Python or R,
trains a model in an external framework, and finally writes the results back.
The cost of this round trip is felt at every stage: data must be moved across
process and language boundaries, the analytical pipeline is fragmented across
several tools, work is duplicated between the database and the framework, and
the database itself loses the opportunity to optimize the combined workload as a
single query. These limitations motivate the integration of automatic
differentiation (AD) directly inside SQL and the database engine.

\section{Automatic Differentiation}

Automatic differentiation computes derivatives by applying the chain rule at the
operation level~\cite{baydin2017automatic,griewank2008evaluating}. It comes in
two main forms. Forward-mode AD propagates derivatives alongside primal values
during expression evaluation, using dual-number arithmetic to carry a partial
derivative through every operation. Reverse-mode AD records the sequence of
operations during a forward pass and then propagates adjoint values back through
that record to produce the gradient with respect to every input.

Reverse-mode AD powers deep learning frameworks~\cite{pearlmutter2008reverse}
such as TensorFlow~\cite{abadi2016tensorflow}, PyTorch~\cite{paszke2019pytorch},
and JAX~\cite{jax2018}. It is the computational basis of gradient-based
optimizers, including stochastic gradient descent and adaptive methods such as
Adam~\cite{kingma2015adam}, and of more advanced uses of the gradient signal
such as gradient-based hyperparameter optimization~\cite{maclaurin2015reversible}.
No relational database currently supports AD natively.

\section{Why AD in SQL?}

Embedding AD inside SQL changes where gradients are computed and what users have
to do to obtain them. Gradients are computed where the data lives, so analytics
and machine learning share a single pipeline and a single execution engine;
gradient-descent loops can be expressed directly in SQL; and the database is
free to optimize the combined computation rather than treating it as an opaque
external step.

The primary objective of the proposed system is not to outperform handwritten
SQL gradients, but to automate gradient computation directly inside the database
system. Manual derivation of SQL gradients becomes increasingly difficult and
error-prone for complex analytical workloads. Automatic differentiation lets
users express differentiable computations declaratively using lambda expressions
while preserving database-native execution.

Prior systems such as MADlib~\cite{madlib}, Bismarck~\cite{feng2012unified},
and SystemML~\cite{boehm2013systemml} support in-database analytics, but still
require manually derived gradients or predefined model templates.
DuckDB~\cite{duckdb2019} supports higher-order functions and vectorized
execution~\cite{raasveldt2022modular}, making it suitable for AD integration.

\section{DuckDB and Higher-Order Lambdas}

DuckDB supports lambda expressions such as \verb|(x -> x * x + 3)|. These treat
expressions as first-class functions, which enables automatic differentiation
over them: the lambda body is precisely the differentiable program whose
gradient the AD system needs to compute.

\section{Problem Statement}

SQL on its own lacks the building blocks required for automatic differentiation.
There is no notion of a computation graph, no mechanism for propagating
derivatives through arithmetic operators, no place to store the intermediate
values that reverse-mode AD relies on, and no AD-capable operators in the scalar
function library. To address this, this thesis implements forward-mode AD using
dual-number propagation, reverse-mode AD using a compiled instruction tape, and
a bind-time tape compilation optimization that ensures the tape is built once
per query and reused for every row.

\section{Research Questions}

This thesis investigates whether automatic differentiation can be efficiently
integrated into a modern analytical database system using higher-order SQL
lambda expressions. The research focuses on the following questions:

\begin{enumerate}
  \item Can higher-order SQL lambda expressions be used to represent
        differentiable computations inside DuckDB?
  \item How can forward-mode and reverse-mode automatic differentiation be
        integrated into DuckDB's query execution pipeline?
  \item Can reverse-mode AD be optimized using bind-time tape compilation and
        reuse?
  \item What performance overhead is introduced by automatic differentiation
        inside SQL queries?
  \item Can vectorized execution in DuckDB efficiently support gradient
        computation over relational data?
\end{enumerate}

These research questions guide both the implementation and the experimental
evaluation presented throughout this thesis.

\section{Thesis Contributions}

The primary contributions of this thesis are as follows. Forward-mode automatic
differentiation is implemented inside DuckDB using higher-order SQL lambda
functions and a flat instruction tape compiled at bind time. Reverse-mode
automatic differentiation is implemented with the same bind-time tape
compilation strategy, together with tape reuse across rows and iterations.
Common subexpression elimination (CSE) is applied to the instruction tape to
remove redundant computations identified at bind time, and tiled vectorisation
of the tape replay improves cache utilization during execution. Both AD modes
are further compiled to native machine code via LLVM JIT compilation, which
eliminates interpreter overhead and achieves $1.00\times$ overhead relative to
handwritten SQL at 50{,}000 tuples. Finally, the thesis presents an
experimental evaluation comparing handwritten SQL gradients, forward-mode AD,
and reverse-mode AD across every optimization stage described above.


\section{Thesis Structure}

The remainder of the thesis is structured as follows. Chapter~\ref{ch:background}
introduces the background on automatic differentiation, differentiable
programming, and machine learning inside database systems. Chapter~\ref{ch:design}
describes DuckDB's architecture and the system design used to integrate AD into
its query pipeline. Chapter~\ref{ch:implementation} presents the implementation
of forward-mode and reverse-mode AD. Chapter~\ref{ch:evaluation} evaluates the
implementation on linear regression workloads. Chapter~\ref{ch:conclusion}
discusses the results, summarizes the contributions, and outlines future work.

\chapter{Background and Related Work}
\label{ch:background}

This chapter discusses the background concepts required for this thesis. The work combines ideas from automatic differentiation, differentiable programming, higher-order SQL functions, and database query execution. Since the implementation was developed inside DuckDB, this chapter also discusses vectorized query execution and machine learning inside database systems.

\section{Automatic Differentiation}

Automatic differentiation (AD) is a technique for computing exact derivatives of functions represented as programs. Unlike symbolic differentiation, AD does not manipulate mathematical expressions directly. Instead, it applies the chain rule during program execution.

Baydin et al.~\cite{baydin2017automatic} provide a detailed survey of AD methods and their applications in machine learning systems. Griewank and Walther~\cite{griewank2008evaluating} formally describe forward-mode and reverse-mode AD and explain how gradients can be propagated through computation graphs. Beyond the first-order gradient, the same operation-level differentiation principle extends to higher-order information, such as exact Hessian-vector products~\cite{pearlmutter1994hessian}, although the present work is restricted to first-order gradients.

AD is used extensively in modern machine learning frameworks, because training algorithms such as gradient descent require efficient gradient computation. Modern systems rely mainly on reverse-mode AD. TensorFlow~\cite{abadi2016tensorflow} uses graph-based execution and symbolic gradient operators, while PyTorch~\cite{paszke2019pytorch} introduced dynamic computation graphs using eager execution. Although these frameworks provide highly optimized differentiation systems, they operate mainly outside relational database engines.

Schüle et al.~\cite{schule2022llvm} integrated forward-mode and
reverse-mode AD as SQL operators inside the Umbra database system,
using LLVM code generation to eliminate interpreter overhead. Their
work demonstrated that after LLVM optimisation, both AD modes
produce nearly identical machine code and achieve equivalent runtime
performance. This thesis independently replicates that finding in
DuckDB using a flat tape intermediate representation compiled
directly to LLVM IR, without requiring the MLIR infrastructure
used in Umbra.

\centering
\includegraphics[width=\linewidth]{ml_frameworks_comparison.pdf}
\caption{Comparison of automatic differentiation support across DuckDB and modern machine learning frameworks.}
\label{fig:ml_frameworks_comparison}
\end{figure}

\section{Differentiable Programming}

Differentiable programming extends AD to general-purpose programming languages. Instead of differentiating only tensor operations, differentiable programming systems attempt to differentiate entire programs, including control flow and data structures.

Recent compiler-based approaches focus on program transformation, graph-level
optimization, the design of intermediate representations, and efficient gradient
compilation~\cite{innes2018adjoint,baudart2021stan}.

These ideas influenced the implementation developed in this thesis, especially the optimization of reverse-mode AD using instruction tapes. The concept of compiling a reusable instruction tape at bind time, rather than rebuilding the computation graph per row, directly reflects tape-based AD compilation strategies. Domain-specific compilers for machine learning, such as TVM~\cite{chen2018tvm}, similarly demonstrate that lowering high-level computations to a compact, optimizable intermediate representation yields substantial runtime benefits.

Most differentiable programming systems, however, focus on tensor programs,
imperative programming languages, or neural-network-oriented computation.

Very little work studies differentiability directly inside SQL query engines or relational algebra execution. A notable exception is the use of differentiable formulations to incorporate relational background knowledge into learning systems~\cite{payani2020relational}, although such work targets logic-based reasoning rather than gradient computation over SQL expressions.

This thesis extends differentiable programming concepts into SQL by enabling gradient computation over higher-order SQL lambda expressions inside DuckDB~\cite{peseux2023differentiable}.

\section{Machine Learning Inside Databases}

There has been significant interest in integrating machine learning functionality directly inside database systems. One major motivation is to avoid unnecessary data movement between storage systems and external machine learning frameworks. Early work even explored embedding neural-network models directly within database systems~\cite{schikuta2008neural}, anticipating the closer coupling of learning and data management seen today.

Early systems include MADlib~\cite{madlib}, which provides SQL-based machine
learning operators for PostgreSQL, and Bismarck~\cite{feng2012unified}, which
introduced a unified architecture for implementing iterative ML and analytical
tasks inside DBMSs.

Large-scale analytical systems such as Spark SQL and MLlib also demonstrated the advantages of combining relational processing with machine learning workloads~\cite{armbrust2015sparksql,zaharia2016spark,meng2016mllib,boehm2016systemml}. These systems build on a broader lineage of large-scale data-processing frameworks, including MapReduce~\cite{dean2004mapreduce}, resilient distributed datasets~\cite{zaharia2012rdd}, declarative dataflow languages such as Pig Latin~\cite{olston2008piglatin}, hybrid MapReduce--DBMS architectures such as HadoopDB~\cite{abouzeid2009hadoopdb}, and interactive web-scale analytical engines such as Dremel~\cite{melnik2010dremel}.

Despite these advances, existing systems typically rely on manually derived
gradients, predefined ML operators, or fixed model templates, rather than
differentiating directly over arbitrary SQL lambda expressions. The need for automation is reinforced by the difficulty of interpreting and trusting model behaviour, a concern that has motivated dedicated explanation techniques~\cite{ribeiro2016trust}: pipelines whose gradients are derived automatically are easier to inspect and reason about than hand-derived ones.

A related but distinct line of work uses machine learning to optimize the database engine itself, rather than exposing ML to users as a query capability. Learned index structures replace traditional index data structures with learned models ~\cite{kraska2018learned}, learned query optimizers use ML to improve plan selection ~\cite{chen2024glo}, and self-driving database systems apply ML throughout the engine for autonomous tuning ~\cite{pavlo2017selfdriving}. This thesis instead focuses on making differentiable computation available as a first-class SQL capability, exposed directly to the user through lambda expressions, rather than on using learning to optimize the engine internally.

\begin{figure}[H]
    \centering
    \includegraphics[width=\linewidth]{ml_database_landscape.pdf}
    \caption{Landscape of machine learning approaches integrated inside database systems.}
    \label{fig:ml_landscape}
\end{figure}

The goal of this thesis is different. Instead of implementing predefined ML algorithms, the work focuses on enabling generic automatic differentiation inside DuckDB queries.

\section{Higher-Order Functions in SQL}

Higher-order SQL functions allow functions or lambda expressions to be passed as arguments to other functions. These features increase the expressiveness of SQL and enable a more functional style of query processing.

DuckDB recently introduced support for higher-order functions and lambda expressions. This enables queries such as:

\begin{lstlisting}[language=SQL]
SELECT transform(col, x -> x * 2) FROM t;
\end{lstlisting}

These lambda functions are important for this thesis because they allow mathematical expressions to be represented directly inside SQL queries.

In this work, lambda expressions are treated as differentiable programs. The AD system extracts the lambda expression during query binding and transforms it into an internal representation used for gradient computation.

\begin{figure}[h]
\centering
\includegraphics[width=\linewidth]{lambda_support_in_sql.pdf}
\caption{Lambda function support in DuckDB: parsing, binding, and use during execution.}
\label{fig:lambda_support_sql}
\end{figure}

This functionality forms the foundation of the implemented AD framework.

\section{Computation Graphs and AD Execution Models}

Reverse-mode AD relies on computation graphs, also known as tapes, that store intermediate operations and their dependencies during execution. During the backward pass, gradients are propagated in reverse order through the graph.

Deep learning systems such as TensorFlow and PyTorch internally build
computation graphs~\cite{agrawal2019eager} that record primitive operations,
intermediate values, and the dependency relationships required for
backpropagation.

The reverse-mode algorithm itself has a long history. Beyond the deep learning frameworks above, it has been studied both as a functional-programming construct~\cite{pearlmutter2008reverse} and in relation to the underlying error-propagation mechanism of backpropagation~\cite{grum2023backprop}.

DuckDB, however, is not a tensor interpreter. It uses a vectorized query execution engine optimized for columnar analytical processing~\cite{raasveldt2022modular}. Integrating reverse-mode AD into this setting therefore required that lambda expressions be converted into executable operation sequences, that intermediate values be stored efficiently, and that gradients be accumulated within execution chunks.

An early version of the reverse-mode implementation rebuilt the computation graph repeatedly during execution, which produced significant runtime overhead.

To remove this overhead, the computation graph is compiled once, during the bind phase, into an instruction tape representation. The tape stores preprocessed operations that are reused during query execution.

This optimization reduced graph reconstruction overhead and substantially improved reverse-mode runtime.

\begin{figure}[h]
\centering
\includegraphics[width=\textwidth]{computation_graph_vs_tape.pdf}
\caption{Comparison between traditional computation graphs and the tape-based reverse-mode implementation used in DuckDB.}
\label{fig:computation_graph_compare}
\end{figure}

This optimization became especially important during the repeated gradient computations in the linear regression benchmarks.

\section{Summary}

This chapter discussed the main background topics required for this thesis, including automatic differentiation, differentiable programming, higher-order SQL functions, and machine learning inside database systems.

Existing systems demonstrate strong interest in combining machine learning and database processing. However, most current approaches rely on predefined operators or external frameworks.

This thesis differs by implementing reusable forward-mode and reverse-mode automatic differentiation directly inside DuckDB using SQL lambda expressions and vectorized query execution.

\chapter{DuckDB Architecture and System Design}
\label{ch:design}

DuckDB is a modern in-process analytical database system designed to efficiently execute OLAP-style workloads. Its lightweight architecture, vectorized query execution, and native support for higher-order SQL functions make it an excellent candidate for integrating automatic differentiation (AD). This chapter introduces the primary system components relevant to understanding how AD is integrated into DuckDB.

\section{Overview of DuckDB}

DuckDB differs from traditional client--server databases by running entirely in-process, eliminating network overhead and simplifying integration with analytical tools such as Python and R~\cite{kohn2022duckdbwasm}. It is optimized for OLAP-style analytical workloads, which differ markedly in their access patterns from the transaction-oriented OLTP workloads targeted by main-memory transactional systems such as VoltDB~\cite{stonebraker2013voltdb} and HyPer~\cite{hyper2011}; the contrasting demands of these two workload classes have themselves been the subject of detailed study~\cite{harizopoulos2008oltp}. Its architecture follows a multi-stage query processing pipeline that includes parsing, binding, logical planning, physical planning, and vectorized execution~\cite{raasveldt2022modular}.

Figure~\ref{fig:duckdb_pipeline} illustrates this pipeline.

\begin{figure}[h]
\centering
\includegraphics[width=\textwidth]{duckdb_pipeline.pdf}
\caption{DuckDB's query processing pipeline~\cite{duckdb2019,raasveldt2022modular}.}
\label{fig:duckdb_pipeline}
\end{figure}

Each stage plays a distinct role in transforming SQL text into executable operators.

\section{Integration into DuckDB Query Pipeline}

The automatic differentiation framework was integrated into DuckDB's existing query processing pipeline. Instead of modifying the complete execution engine, the implementation extends DuckDB's scalar function subsystem.

The execution flow proceeds in five stages: SQL query parsing, lambda
expression binding, construction of differentiable expressions, forward-mode or reverse-mode AD execution, and finally vectorized result generation. The
implementation reuses DuckDB's vectorized execution engine and operates
directly on \texttt{DataChunk} structures during query execution.

\section{Parsing and Lambda Expressions}

DuckDB supports higher-order SQL functions and lambda expressions, enabling functional programming constructs inside SQL. A lambda such as:

\begin{lstlisting}[language=SQL]
(x -> x + 1)
\end{lstlisting}

\ldots is parsed into a \texttt{LambdaExpression} AST node that stores a list of
parameters, a body expression, and any captured variables. These abstract
syntax trees form the structural representation required by AD.
Figure~\ref{fig:lambda_ast} shows a simplified representation of the lambda
AST.

\begin{figure}[h]
\centering
\includegraphics[width=\textwidth]{lambda_ast.pdf}
\caption{Simplified lambda expression AST structure.}
\label{fig:lambda_ast}
\end{figure}

\subsection{Lambda Parameter Binding}

During implementation, lambda expressions required explicit parameter resolution during the binding phase. DuckDB internally represents lambda references using bound expressions, but parameter references were not always consistently mapped across different expression types.

To resolve this, a helper mechanism named \texttt{NameToSlot()} was introduced. The function maps lambda parameter names to the internal parameter indices used during derivative seeding:

\begin{lstlisting}[language=C++]
static bool NameToSlot(
    const string &raw_in,
    idx_t param_cnt,
    idx_t &slot_out);
\end{lstlisting}

This mapping allowed automatic differentiation to correctly associate each lambda parameter with its corresponding derivative vector entry.

\section{Binder: Central Integration Point for AD}

The binder performs semantic analysis, resolves identifiers, infers types, rewrites expressions, and ensures SQL validity. It is also the earliest stage at which a complete expression tree is available. Reverse-mode AD requires constructing a computation graph, or tape, that captures the order of operations~\cite{griewank2008evaluating,baydin2017automatic}. Because binding happens once per query rather than once per row, it is the ideal place to compile this graph.

The AD extension adds binder logic that extracts the expression tree from a
lambda, traverses it once, and builds a reusable computation tape for
reverse-mode AD.

Performing this work in the binder is necessary because lambda references are not always bound consistently across different expression types inside DuckDB, and the binder is the first stage at which the complete, resolved expression tree can be inspected. Shifting work from the per-row execution path to a single binding-time step mirrors the design philosophy of query compilers, which similarly specialize a query before execution to avoid repeated interpretation overhead~\cite{shaikhha2016compiler,tahboub2018compiler}.

Figure~\ref{fig:binder_workflow} shows the binder workflow.

\begin{figure}[h]
\centering
\includegraphics[width=\textwidth]{binder_workflow.pdf}
\caption{Extended binder workflow with reverse-mode AD tape compilation~\cite{griewank2008evaluating}.}
\label{fig:binder_workflow}
\end{figure}

Compiling the tape in the binder significantly improves execution performance, because the tape is then reused for every input row instead of being rebuilt.

\section{Logical and Physical Planning}

After binding, DuckDB builds a logical plan composed of operators such as:

\begin{itemize}
    \item \texttt{LogicalGet} (table scan),
    \item \texttt{LogicalProjection},
    \item \texttt{LogicalFilter},
    \item \texttt{LogicalAggregate}.
\end{itemize}

This planning model is related to classical relational query optimization and execution techniques~\cite{selinger1979access,graefe1993query,neumann2011efficiently,chaudhuri1998optimization,graefe1994volcano}. The interaction between query plans and application code has also been studied from the opposite direction, by synthesizing relational queries from imperative programs~\cite{cheung2013synthesis}, which underscores how closely program structure and query structure are related.

AD-based lambda expressions appear as scalar functions inside projections. The physical planner converts the logical plan into vectorized physical operators~\cite{raasveldt2022modular}, and the AD functions \texttt{mygrad\_fwd} and \texttt{mygrad\_rev} execute inside the \texttt{PhysicalExpressionExecutor}.

\section{Vectorized Execution}

DuckDB's vectorized execution model evaluates operators on \texttt{DataChunk} structures, which typically contain up to 2048 values per column. Each chunk consists of column vectors that are processed efficiently using SIMD-style optimizations~\cite{raasveldt2022modular,kersten2018vectorized,boncz2008monetdb}. This columnar, chunk-at-a-time execution style builds on a long line of work on column-oriented and main-memory database systems~\cite{stonebraker2005cstore,abadi2006compression,harizopoulos2006readoptimized,manegold2002mainmemory}, including strategies for efficiently merging differential update stores into column-oriented in-memory engines~\cite{hubner2011differential}, and on NUMA-aware parallel query evaluation~\cite{leis2014morsel}.

Figure~\ref{fig:vectorized_execution} shows this model.

\begin{figure}[h]
\centering
\includegraphics[width=\textwidth]{vectorized_execution.pdf}
\caption{Vectorized execution model used in DuckDB~\cite{raasveldt2022modular}.}
\label{fig:vectorized_execution}
\end{figure}

The AD system integrates into this model at the scalar-function level. The AD functions are invoked once per data chunk: forward-mode AD propagates derivative information alongside the primal values, and reverse-mode AD executes a primal pass followed by adjoint propagation over the compiled tape. Within a chunk, the compiled tape is replayed for each row; the performance implications of this are discussed in Chapter~\ref{ch:conclusion}.

\section{Full AD Integration Across DuckDB}

Figure~\ref{fig:system_architecture} presents the overall system architecture,
which integrates DuckDB's binder and planner, the AD extension layer,
forward-mode and reverse-mode AD, and vectorized runtime execution. This
architecture allows differentiable SQL expressions to be evaluated using
DuckDB's native execution pipeline.

\begin{figure}[h]
\centering
\includegraphics[width=\textwidth]{system_architecture.pdf}
\caption{Overall architecture of the AD extension in DuckDB, integrating forward-mode and reverse-mode AD with higher-order SQL functions~\cite{raasveldt2022modular,baydin2017automatic}.}
\label{fig:system_architecture}
\end{figure}

\section{Summary}

This chapter described DuckDB's architecture and its relevance to integrating AD functionality. The binder provides the crucial entry point for extracting expression trees and compiling reverse-mode AD tapes. The logical and physical planning stages incorporate AD into the execution plan, while DuckDB's vectorized execution engine evaluates both primal values and gradients. During implementation, understanding the binder stage was particularly important, because this is where the lambda expression tree becomes accessible for tape compilation. Chapter~\ref{ch:evaluation} evaluates the performance of these AD mechanisms through empirical experiments.

\chapter{Implementation}
\label{ch:implementation}

\section{Overview}

This chapter describes the implementation of automatic differentiation (AD) inside DuckDB using higher-order SQL lambda functions. The goal of the implementation was to support gradient computation directly within SQL queries without relying on external machine learning frameworks.

The implementation was developed directly inside the DuckDB source tree in C++. The AD functionality was integrated into DuckDB's scalar function framework and reused the existing parser, binder, and vectorized execution engine provided by DuckDB~\cite{duckdb2019}.

Two differentiation approaches were implemented:

\begin{itemize}
     \item Forward-mode AD
     \item Reverse-mode AD
\end{itemize}

Both approaches operate on lambda expressions written directly in SQL queries, and both return the full gradient of the lambda expression in a single call.

\section{Forward-Mode Automatic Differentiation}

Forward-mode AD propagates derivative information alongside primal values during expression evaluation. Conceptually, each value is extended into a dual number:

\begin{equation}
(v, \dot{v})
\label{eq:dual-number}
\end{equation}

where \(v\) is the original value and \(\dot{v}\) is its derivative.

In the implemented design, a single scalar derivative is generalised to a vector of partial derivatives, so that the partials with respect to all lambda parameters can be propagated in one evaluation pass. Each intermediate value therefore stores the computed scalar value together with a gradient vector. This is represented by the following structure:

\begin{lstlisting}[language=C++]
struct Dual {
    double val;
    std::vector<double> grad;
};
\end{lstlisting}

Arithmetic operators for addition, subtraction, multiplication, and division were overloaded to propagate derivatives according to the chain rule. Because the gradient vector carries one entry per parameter, the cost of forward-mode evaluation grows with the number of parameters; this property is analysed further in Appendix~\ref{app:proofs} and is reflected in the experimental results in Chapter~\ref{ch:evaluation}.


\section{Bind-Time Operator Resolution}

An early version of the forward-mode evaluator dispatched arithmetic
operators by performing string operations on every operator in every
row: \texttt{StringUtil::Lower(ExpressionTypeToString(expr.type))} followed
by several substring searches to determine whether the operator was
ADD, SUB, MUL, or DIV. For an expression of approximately 50 operators
evaluated over 50{,}000 rows for 20 gradient-descent iterations, this
amounted to tens of millions of string operations per benchmark run
and dominated the forward-mode runtime.

The optimized design moves this work to the bind phase. During binding,
the expression tree is walked once and each operator's kind is resolved
into a compact \texttt{OpKind} enum, cached in a hash map keyed by the
expression pointer:

\begin{lstlisting}[language=C++]
enum class OpKind { ADD, SUB, MUL, DIV, NEG, UNKNOWN };

struct AutoDiffGradBindData : public FunctionData {
    unique_ptr<Expression> lambda_expr;
    idx_t param_cnt;
    std::unordered_map<Expression*, OpKind> op_cache;
    // ...
};
\end{lstlisting}

At execution time, \texttt{EvalExpr} performs a single hash-map lookup
followed by a \texttt{switch} statement on the enum, with no per-row
string operations:

\begin{lstlisting}[language=C++]
auto it = bind.op_cache.find(&expr);
OpKind kind = (it != bind.op_cache.end())
              ? it->second : OpKind::UNKNOWN;

switch (kind) {
case OpKind::ADD: return Add(L, R);
case OpKind::SUB: return Sub(L, R);
case OpKind::MUL: return Mul(L, R);
case OpKind::DIV: return Div(L, R);
case OpKind::NEG: return Neg(L);
default:
    throw BinderException("mygrad: unsupported operator");
}
\end{lstlisting}

This mirrors the design philosophy of the reverse-mode AD's compiled
instruction tape: expensive analysis is performed once at bind time
and replayed cheaply per row. The effect of this optimization on
runtime is reported in Chapter~\ref{ch:evaluation}.

\section{Expression Evaluation}

DuckDB internally represents SQL expressions as expression trees. The implementation recursively traverses these expression trees and propagates derivative information through the computation.

The following expression types are supported:

\begin{itemize}
    \item Constants
    \item Column references
    \item Arithmetic operators
    \item Unary negation
    \item Cast expressions
\end{itemize}

Unsupported expressions raise runtime exceptions during query execution.

\section{Lambda Function Integration}

Higher-order lambda functions are used to represent differentiable computations directly inside SQL queries. The AD function receives a list of numeric arguments followed by a lambda expression. The lambda declares one parameter per numeric argument, in the same positional order, and its body may refer only to those declared parameters. The AD function returns a structured value holding one partial derivative per argument; the gradient with respect to the trainable parameters is read from the corresponding struct fields.

An example forward-mode query is shown below:

\begin{lstlisting}[language=SQL]
SELECT mygrad_fwd(
    a1, a2, x1, y,
    (p1, p2, p3, p4) ->
        (p1 * p3 + p2 - p4) * (p1 * p3 + p2 - p4)
)
FROM data;
\end{lstlisting}

For readability, the example above uses a simplified four-parameter lambda expression. The actual benchmark workload described in Chapter~\ref{ch:evaluation} uses six trainable weights and one bias parameter.

During binding, the lambda expression is extracted from the function arguments and stored in internal bind data structures for use during execution.

\section{Parameter Mapping}

One implementation challenge involved mapping lambda parameter names to gradient slots.

In some cases, DuckDB represented lambda variables as generic bound references rather than positional parameters. To resolve this, a name-based mapping helper was implemented:

\begin{lstlisting}[language=C++]
static bool NameToSlot(const string &raw_in,
                       idx_t param_cnt,
                       idx_t &slot_out);
\end{lstlisting}

This function maps lambda parameter names such as \texttt{p1}, \texttt{p2}, or \texttt{p3} to the corresponding gradient index used during derivative seeding.

\section{Reverse-Mode Automatic Differentiation}

Reverse-mode AD was implemented using a compiled instruction tape and backward propagation~\cite{baydin2017automatic}.

Rather than interpreting the lambda expression tree directly, the expression is compiled into a flat sequence of primitive operations. Each operation is represented by a compact record storing the operation kind and the indices of its operand operations:

\begin{lstlisting}[language=C++]
struct CompiledOp {
    OpKind  op;          // INPUT, CONST, NEG, ADD, SUB, MUL, DIV
    int32_t a, b;        // operand indices into the program
    double  cval;        // constant value (CONST only)
    int32_t input_slot;  // parameter slot (INPUT only)
};
\end{lstlisting}

The compiled program is a single \texttt{std::vector<CompiledOp>}, which is contiguous in memory and indexed by integer position rather than traversed through pointers. Evaluation proceeds in two phases. During the forward pass, the operations are evaluated in order and their primal values stored. During the backward pass, the program is traversed in reverse, and adjoint values are accumulated into each operand according to the local derivative rule of each operation.

\subsection{Bind-Time Tape Compilation and Reuse}

An early version of the reverse-mode implementation reconstructed the computation graph during query execution. Because the same lambda expression structure was analysed repeatedly, this introduced significant overhead for larger datasets.

To remove this overhead, the expression tree is compiled into the instruction tape exactly once, during the binding phase. Binding occurs once per query rather than once per row, so the compiled tape is produced a single time and stored in the function's bind data. During execution the tape is only read; it is not rebuilt. The tape is therefore shared across every gradient-descent iteration and every processed row.

This optimization eliminates repeated graph construction and is the most important performance improvement implemented in this work. Its effect is discussed in Chapter~\ref{ch:evaluation} and Appendix~\ref{app:experiments}.

\subsection{Gradient Descent in SQL Using AD}

Listing~\ref{lst:gd-comparison} shows gradient descent expressed
in SQL using both handwritten gradients and the implemented AD
operator, following the style of Schüle et al.~\cite{schule2022llvm}.

\begin{lstlisting}[language=SQL, caption={Gradient descent using
recursive tables: manually derived (lines 1--8) and using automatic
differentiation (lines 10--20).}, label={lst:gd-comparison}]
-- Handwritten SQL gradients (baseline)
WITH RECURSIVE gd(i, a1, a2, a3, a4, a5, a6, b) AS (
  SELECT 1, 1.0::DOUBLE, 1.0::DOUBLE, 1.0::DOUBLE,
            1.0::DOUBLE, 1.0::DOUBLE, 1.0::DOUBLE, 1.0::DOUBLE
  UNION ALL
  SELECT i+1,
    a1 - 0.1*AVG(2*x1*(a1*x1+a2*x2+a3*x3+a4*x4+a5*x5+a6*x6+b-y6)),
    ...
    b  - 0.1*AVG(2*(a1*x1+a2*x2+a3*x3+a4*x4+a5*x5+a6*x6+b-y6))
  FROM gd, data WHERE i < 20 GROUP BY i,a1,a2,a3,a4,a5,a6,b
)
SELECT * FROM gd WHERE i = 20;

-- Automatic differentiation using mygrad_rev
WITH RECURSIVE gd(i, a1, a2, a3, a4, a5, a6, b) AS (
  SELECT 1, 1.0::DOUBLE, 1.0::DOUBLE, 1.0::DOUBLE,
            1.0::DOUBLE, 1.0::DOUBLE, 1.0::DOUBLE, 1.0::DOUBLE
  UNION ALL
  SELECT i+1,
    a1 - 0.1*AVG(g.d1), a2 - 0.1*AVG(g.d2),
    a3 - 0.1*AVG(g.d3), a4 - 0.1*AVG(g.d4),
    a5 - 0.1*AVG(g.d5), a6 - 0.1*AVG(g.d6),
    b  - 0.1*AVG(g.d7)
  FROM (
    SELECT mygrad_rev(
      gd.a1,gd.a2,gd.a3,gd.a4,gd.a5,gd.a6,gd.b,
      data.x1,data.x2,data.x3,data.x4,data.x5,data.x6,data.y6,
      (p1,p2,p3,p4,p5,p6,p7,p8,p9,p10,p11,p12,p13,p14) ->
        (p1*p8+p2*p9+p3*p10+p4*p11+p5*p12+p6*p13+p7-p14)
       *(p1*p8+p2*p9+p3*p10+p4*p11+p5*p12+p6*p13+p7-p14)
    ) AS g
    FROM gd, data WHERE gd.i < 20
  )
  GROUP BY i,a1,a2,a3,a4,a5,a6,b
)
SELECT * FROM gd WHERE i = 20;
\end{lstlisting}

\subsection{Storing Lambda Expressions in Tables}
\label{sec:stored-lambda}

The lambda expressions used throughout this thesis so far are written inline
in the SQL query text, following the same pattern as DuckDB's native
higher-order functions. Following the supervisor's suggestion, this section
extends the implementation so that a lambda expression can also be stored as
a value in a table column, retrieved via a query, and passed to
\texttt{mygrad\_fwd} or \texttt{mygrad\_rev} without being written inline.

\subsubsection{A New Logical Type: \texttt{STORED\_LAMBDA}}

DuckDB's type system (\texttt{LogicalTypeId}) was extended with a new type,
\texttt{STORED\_LAMBDA}, following the same registration pattern used for
existing types such as \texttt{BIT}. The type is physically backed by
\texttt{VARCHAR} storage, is registered as a nameable SQL type (so
\texttt{col STORED\_LAMBDA} can appear in a \texttt{CREATE TABLE} statement),
and has explicit cast rules allowing a string literal to be implicitly
converted into it:

\begin{lstlisting}[language=SQL]
CREATE TABLE models (name VARCHAR, loss_fn STORED_LAMBDA);
INSERT INTO models VALUES (
    'linear',
    '(p1,p2,p3,p4) -> (p1*p3+p2-p4)*(p1*p3+p2-p4)'
);
\end{lstlisting}

Unlike a plain \texttt{VARCHAR} column, \texttt{STORED\_LAMBDA} is a distinct,
named type in the catalog and in query results (\texttt{typeof()} reports it
as \texttt{STORED\_LAMBDA}), giving lambda values first-class type status
comparable to DuckDB's \texttt{LIST} type, while keeping the underlying
storage simple.

\subsubsection{Parsing a Stored Lambda}

A stored lambda is held as text of the form \texttt{(p1,...,pN) -> body}.
Because DuckDB's grammar only recognises the \texttt{->} lambda syntax inside
a higher-order function call, a stored lambda's text cannot be parsed by
DuckDB's parser as a whole. Instead, the parameter list and body are split
manually, and only the body is handed to DuckDB's expression parser
(\texttt{Parser::ParseExpressionList}), which returns a genuine, unbound
expression tree. This unbound tree is then compiled into the same flat
instruction tape representation (\texttt{CompiledOp}/\texttt{FwdOp}) used for
inline lambdas, so that all downstream machinery --- common subexpression
elimination, symbolic differentiation, and LLVM JIT compilation --- is
reused unchanged for both inline and stored lambdas.

\subsubsection{Two Execution Paths}

Two distinct cases are handled, depending on when the lambda's text becomes
known:

\begin{itemize}
    \item \textbf{Bind-time (constant) path.} When the stored lambda argument
    is a literal cast to \texttt{STORED\_LAMBDA} (or any expression DuckDB's
    optimiser constant-folds before binding), the text is known at bind time.
    In this case the lambda is parsed, compiled, CSE-reduced, and JIT-compiled
    exactly once, identically to the inline-lambda path, and reused for every
    row --- achieving the same performance characteristics reported in
    Chapter~5.

    \item \textbf{Execution-time (dynamic) path.} When the stored lambda
    argument is a column reference or the result of a join --- as in
    \texttt{mygrad\_rev(data.*, models.loss\_fn) FROM data, models} --- its
    text is genuinely per-row data and cannot be known at bind time. In this
    case, the bind function marks the call as \emph{dynamic}, and at
    execution time each row's lambda text is parsed and compiled lazily, with
    the compiled tape cached in a hash map keyed by the lambda's text. Rows
    sharing the same stored lambda therefore reuse the same compiled tape,
    while rows with a different stored lambda trigger a new
    parse-and-compile step exactly once.
\end{itemize}

\begin{lstlisting}[language=SQL]
SELECT mygrad_rev(data.x1, data.x2, data.x3, data.x4, models.loss_fn)
FROM data, models
WHERE models.name = data.model_name;
\end{lstlisting}

\subsubsection{Verification}

Both execution paths were verified against hand-derived analytical gradients.
For the loss function
$L = (p_1 p_3 + p_2 - p_4)^2$
evaluated at $(p_1,p_2,p_3,p_4) = (1,2,3,4)$, both the bind-time and
execution-time paths produced $(6.0, 2.0, 2.0, -2.0)$, matching the
analytical gradient exactly. A second test joined two different stored
lambdas (a four-parameter and a two-parameter model) against separate data
tables in the same session, confirming that the per-row cache correctly
distinguishes between different stored lambda texts rather than reusing a
single cached tape incorrectly.This verification was performed for both \texttt{mygrad\_fwd} and
\texttt{mygrad\_rev}: the bind-time and execution-time paths were confirmed
independently for each mode, all four returning $(6.0, 2.0, 2.0, -2.0)$ for
the same test case.

\subsubsection{Scope and Limitations}

The dynamic execution path evaluates each row independently, without the
tiled vectorisation or LLVM JIT compilation applied to the static inline- and
constant-lambda paths, since a JIT compilation step per row would be far more
expensive than the row itself. This was confirmed experimentally for both AD
modes, using the same 20-iteration gradient-descent benchmark and dataset
sizes used throughout Chapter~\ref{ch:evaluation}
(Figure~\ref{fig:stored_lambda_bench}). At 50{,}000 tuples: the reverse-mode
bind-time (constant) path measured 0.093\,s and the reverse-mode dynamic path
0.189\,s (a $2.03\times$ overhead); the forward-mode bind-time (constant)
path measured 0.088\,s and the forward-mode dynamic path 0.350\,s (a
$3.98\times$ overhead). All constant-path measurements match the fully
optimized inline-lambda and handwritten-SQL baselines (0.10\,s at this
scale), confirming that the bind-time path carries no cost regardless of AD
mode.

The dynamic path shows a markedly larger overhead for forward mode than for
reverse mode --- nearly twice the relative slowdown. This is consistent with
the complexity difference between the two modes analysed in
Appendix~\ref{app:proofs}: forward-mode evaluation cost scales as
$O(n \cdot p)$ in the number of parameters $p$, while reverse-mode scales as
$O(n)$. In the fully optimized static paths this difference is masked by
LLVM JIT compilation, which both modes benefit from equally; the dynamic
path has no such compilation step, so the underlying per-parameter cost of
forward-mode AD becomes directly visible in the measured runtime. This path
trades some performance for generality, and is appropriate for workloads
where the lambda genuinely varies across rows (e.g. selecting between a
small number of stored models via a join) rather than for large-scale
single-model training.

\section{Reverse-Mode Execution Workflow}

The overall reverse-mode workflow separates the one-time tape compilation in the binder from the per-row replay in the execution engine, as shown in Algorithm~\ref{alg:reverse-ad}.

\begin{algorithm}
\caption{Reverse-Mode AD with Bind-Time Tape Reuse}
\label{alg:reverse-ad}
\begin{algorithmic}
\State \textbf{Bind phase (once per query):}
\State \quad Parse and bind the lambda expression
\State \quad Compile the expression tree into an instruction tape
\State \quad Store the compiled tape in the function bind data
\State \textbf{Execution phase (per data chunk):}
\State \quad Allocate primal and adjoint buffers once for the chunk
\ForAll{rows in the chunk}
    \State Reset the adjoint buffer
    \State Execute the forward pass over the tape, storing primal values
    \State Seed the adjoint of the output operation with $1.0$
    \State Execute the backward pass over the tape, accumulating adjoints
    \State Emit the parameter gradients for the row
\EndFor
\end{algorithmic}
\end{algorithm}

\section{Algorithmic Description of AD Modes}

Following the algorithmic formulation of Schüle et
al.~\cite{schule2022llvm}, both AD modes apply the chain rule
$\frac{\partial f(g)}{\partial x} = \frac{\partial f(g)}{\partial g}
\cdot \frac{\partial g}{\partial x}$ at each operation.

Algorithm~\ref{alg:fwd-mode} shows forward-mode AD, which
evaluates the expression and derivative simultaneously in one pass,
returning a pair of value and derivative for each subexpression.

\begin{algorithm}[H]
\caption{Forward Mode AD (after Schüle et al.~\cite{schule2022llvm})}
\label{alg:fwd-mode}
\begin{algorithmic}
\Function{eval}{$Z$, $V$}
    \If{$\text{isVariable}(Z)$}
        \If{$Z = V$} \Return $\{z, 1\}$
        \Else\ \Return $\{z, 0\}$
        \EndIf
    \Else
        \State $\{x, x'\} \leftarrow \text{eval}(X, V)$;
               $\{y, y'\} \leftarrow \text{eval}(Y, V)$
        \If{$Z = X + Y$} \Return $\{x+y,\ x'+y'\}$
        \ElsIf{$Z = X - Y$} \Return $\{x-y,\ x'-y'\}$
        \ElsIf{$Z = X \cdot Y$} \Return $\{x \cdot y,\ x' \cdot y + x \cdot y'\}$
        \ElsIf{$Z = X / Y$} \Return $\left\{\frac{x}{y},\ \frac{x' \cdot y - x \cdot y'}{y^2}\right\}$
        \ElsIf{$Z = X^Y$ (w.r.t. $x$)} \Return $\{x^y,\ y \cdot x^{y-1} \cdot x'\}$
        \EndIf
    \EndIf
\EndFunction
\end{algorithmic}
\end{algorithm}

Algorithm~\ref{alg:rev-mode} shows reverse-mode AD, which first
evaluates the expression and then recursively propagates adjoint
values (seeds) backwards through the computation graph.

\begin{algorithm}[H]
\caption{Reverse Mode AD (after Schüle et al.~\cite{schule2022llvm})}
\label{alg:rev-mode}
\begin{algorithmic}
\Function{derive}{$Z$, $z'$}
    \If{$Z = X + Y$}
        \State \Call{derive}{$X$, $z'$};\ \Call{derive}{$Y$, $z'$}
    \ElsIf{$Z = X - Y$}
        \State \Call{derive}{$X$, $z'$};\ \Call{derive}{$Y$, $-z'$}
    \ElsIf{$Z = X \cdot Y$}
        \State \Call{derive}{$X$, $z' \cdot y$};\ \Call{derive}{$Y$, $z' \cdot x$}
    \ElsIf{$Z = X / Y$}
        \State \Call{derive}{$X$, $z'/y$};\ \Call{derive}{$Y$, $-z' \cdot x / y^2$}
    \ElsIf{$Z = X^Y$}
        \State \Call{derive}{$X$, $z' \cdot y \cdot x^{y-1}$};\ 
               \Call{derive}{$Y$, $z' \cdot x^y \cdot \ln(x)$}
    \ElsIf{$\text{isVariable}(Z)$}
        \State $\frac{\partial}{\partial z} \leftarrow \frac{\partial}{\partial z} + z'$
    \EndIf
\EndFunction
\end{algorithmic}
\end{algorithm}

\section{Common Subexpression Elimination}

An analysis of the compiled instruction tape revealed that the benchmark
expression \texttt{(expr) * (expr)} caused the inner subexpression to appear
twice in the tape, resulting in 41 operations for the linear regression loss
function. Common subexpression elimination (CSE) was applied at bind time to
detect and merge structurally identical nodes.

The CSE pass assigns a canonical key to each compiled operation based on its
kind, operand indices, and constant value. Operations with identical keys are
merged into a single node, and all references to the duplicate are redirected
to the merged node:

\begin{lstlisting}[language=C++]
auto make_key = [&](const CompiledOp &op,
                    int32_t ra, int32_t rb) -> std::string {
    char buf[64];
    snprintf(buf, sizeof(buf), "%d:%d:%d:%d:%.17g",
             (int)op.op, ra, rb, op.input_slot, op.cval);
    return std::string(buf);
};
\end{lstlisting}

After CSE, the tape was reduced from 41 to 21 operations for the benchmark
expression. This reduction directly halves the work performed during both
the forward and backward passes of reverse-mode AD.

\section{Tiled Vectorisation}

To improve cache locality during tape replay, a tiled vectorisation strategy
was introduced for reverse-mode AD. Instead of processing one row at a time
through the full tape, rows are grouped into tiles of 256, sized so that the
working set fits within the CPU's L2 cache.

Within each tile, the forward and backward passes are restructured as
operation-outer, row-inner loops:

\begin{lstlisting}[language=C++]
static constexpr idx_t MYGRAD_REV_TILE_SIZE = 256;

for (idx_t tile_start = 0; tile_start < count;
     tile_start += TILE) {
    const idx_t tc = std::min(TILE, count - tile_start);
    // Forward pass: for each op, process all rows in tile
    for (idx_t i = 0; i < prog.size(); i++) {
        for (idx_t r = 0; r < tc; r++) {
            vals[i * TILE + r] = ...;
        }
    }
    // Backward pass: for each op in reverse,
    // process all rows in tile
}
\end{lstlisting}

This layout keeps the working set for each operation contiguous in memory,
improving cache utilization compared to the row-at-a-time layout.

\section{Flat Tape Compilation for Forward Mode}

Forward-mode AD was initially implemented by recursively traversing the
expression tree for every input row, performing string-based operator dispatch
at each node. To eliminate this per-row overhead, the expression tree is
compiled at bind time into the same flat instruction tape format used by
reverse-mode AD.

The forward tape uses a dedicated operation type:

\begin{lstlisting}[language=C++]
enum class FwdOpKind : uint8_t {
    INPUT, CONST, ADD, SUB, MUL, DIV, NEG, POW
};

struct FwdOp {
    FwdOpKind op;
    int32_t a = -1, b = -1;
    int32_t input_slot = -1;
    double  cval = 0.0;
};
\end{lstlisting}

CSE is also applied to the forward tape at bind time, using the same key-based
deduplication approach as for the reverse-mode tape. At runtime, the tape is
evaluated linearly, carrying a \texttt{Dual} value per node that holds both
the primal value and the gradient vector.

\section{LLVM JIT Compilation}

Tape replay, even in its optimized tiled form, still incurs interpreter
overhead: a switch-case dispatch per operation and indirect memory accesses
through the tape array. To eliminate this overhead, LLVM just-in-time
compilation was integrated to compile the instruction tape into native machine
code at bind time.

LLVM version 18 was installed and linked into the DuckDB build. The C++
standard was upgraded from C++11 to C++17 to satisfy LLVM's header
requirements.

\subsection{Namespace Separation}

DuckDB defines its own \texttt{Function}, \texttt{Value}, and \texttt{Type}
classes inside \texttt{namespace duckdb}. LLVM defines identically named
classes. Using LLVM inside \texttt{namespace duckdb} therefore causes
ambiguous name resolution errors.

The JIT code was placed in two separate translation units outside
\texttt{namespace duckdb}:

\begin{itemize}
    \item \texttt{autodiff\_jit.cpp} — JIT compilation for forward-mode AD
    \item \texttt{autodiff\_rev\_jit.cpp} — JIT compilation for reverse-mode AD
\end{itemize}

Each file exposes a bridge function callable from \texttt{namespace duckdb}:

\begin{lstlisting}[language=C++]
// In autodiff_jit.cpp (outside namespace duckdb)
JitFuncType CompileJITBridge(const void* prog_ptr,
                              int32_t root,
                              uint64_t N);
\end{lstlisting}

The main AD files call this bridge at bind time, passing the tape as a void
pointer, and store the returned native function pointer in the bind data for
use at runtime.

\subsection{Forward-Mode JIT}

The forward-mode JIT function in \texttt{autodiff\_jit.cpp} receives the flat
forward tape and generates LLVM IR for each operation. For each input node,
it emits a load from the input array and initializes the gradient vector with
a one-hot seed. For each arithmetic node, it emits the corresponding LLVM
floating-point instruction and propagates gradients according to the chain rule.

At runtime, one call to the compiled native function processes one row,
reading from the input array and writing all gradients to the output array
directly:

\begin{lstlisting}[language=C++]
// Generated native function signature:
using JitFuncType = void(*)(const double* inputs,
                             double* gradients);
\end{lstlisting}

\subsection{Reverse-Mode JIT}

The reverse-mode JIT function in \texttt{autodiff\_rev\_jit.cpp} compiles both
the forward pass and the backward pass of the tape into a single native
function. The forward pass generates LLVM IR values for each tape operation
and stores them as SSA values. The backward pass allocates adjoint accumulators
using LLVM \texttt{alloca} instructions and generates load-accumulate-store
sequences for each operation in reverse order.

A self-referential node fix is required when both operands of a binary
operation refer to the same tape node (as occurs in \texttt{(expr)*(expr)}
after CSE). In this case, both gradient contributions must be accumulated
before any store:

\begin{lstlisting}[language=C++]
if (pa == pb) {
    // Both operands are the same node:
    // accumulate both contributions at once
    Value *ca = B.CreateLoad(dbl, adj[pa]);
    B.CreateStore(
        B.CreateFAdd(ca,
            B.CreateFMul(a_i,
                B.CreateFAdd(lv, rv))),
        adj[pa]);
}
\end{lstlisting}

\subsection{Runtime Execution with JIT}

At bind time, the JIT bridge compiles the tape and stores the resulting
function pointer in the bind data. At runtime, the execute function checks
for a non-null function pointer and, if present, calls the native function
directly for each row:

\begin{lstlisting}[language=C++]
if (bind.jit_func) {
    auto fn = (JitFuncType)bind.jit_func;
    std::vector<double> inputs(N), grads(N);
    for (idx_t r = 0; r < count; r++) {
        for (idx_t j = 0; j < N; j++)
            inputs[j] = in.Get(j, r);
        fn(inputs.data(), grads.data());
        for (idx_t j = 0; j < N; j++)
            out_ptr[j][r] = grads[j];
    }
}
\end{lstlisting}

If JIT compilation fails at bind time, the implementation falls back to the
tiled tape interpreter transparently.

\subsection{Effect of noalias on Generated LLVM IR}

Schüle et al.~\cite{schule2022llvm} observed that without the
\texttt{noalias} attribute on pointer parameters, LLVM cannot
determine whether input and output pointers refer to separate
memory locations. As a result, loads are repeated after every store,
preventing subexpression reuse across gradient outputs.

Figure~\ref{fig:llvm-noalias} illustrates the difference. Without
\texttt{noalias}, the inner expression
$2 \cdot (w_0 \cdot x_0 + x_1 \cdot w_1 + b - y)$
is recomputed separately for each gradient output. With
\texttt{noalias}, LLVM recognises that the pointers are disjoint
and reuses the computed value across both gradient stores.

\centering
\begin{minipage}{0.48\textwidth}

%t6 = fmul double %t5, 2.0

%w0b = load double, double* %pw0

the JIT function reads all inputs before performing any writes,
so the aliasing problem is avoided by construction. The
\texttt{noalias} observation from Schüle et al.~\cite{schule2022llvm}
motivated the design choice of separating input reads from gradient
writes in the generated LLVM IR.

\section{Summary}

This chapter described the complete implementation of automatic differentiation inside DuckDB, including all optimization stages. The implementation proceeded from a basic recursive tree evaluator through bind-time operator caching, flat tape compilation, common subexpression elimination, tiled vectorisation, and finally LLVM JIT compilation. Each stage eliminated a specific source of overhead. The final implementation compiles the AD computation to native machine code at bind time, so that runtime execution requires only a direct function call per row with no interpreter overhead.

\section{Modified DuckDB Components}

The implementation required modifications to the following DuckDB source files:

\begin{itemize}
    \item \texttt{src/function/scalar/generic/autodiff\_grad.cpp}
    \item \texttt{src/function/scalar/generic/autodiff\_reverse.cpp}
    \item \texttt{src/function/scalar/generic/duckdb\_func\_generic.cpp}
\end{itemize}

The AD functions were integrated into DuckDB's scalar function framework and registered using \texttt{ScalarFunctionSet}.

\subsection{Function Registration}

The forward-mode and reverse-mode functions were registered under separate names:

\begin{lstlisting}[language=C++]
ScalarFunctionSet fwd_set("mygrad_fwd");
ScalarFunctionSet rev_set("mygrad_rev");
\end{lstlisting}

Initially, benchmark queries referenced the name \texttt{mygrad}, which did not correspond to any registered function and caused catalog errors during execution. The benchmark scripts were updated to use the registered names \texttt{mygrad\_fwd} and \texttt{mygrad\_rev} explicitly.

\section{Integration with Vectorized Execution}

DuckDB executes queries using vectorized processing~\cite{duckdb2019}. Instead of processing one tuple at a time, the engine evaluates operators over chunks of tuples.

The AD implementation integrates with this model at the scalar-function level. For each data chunk, the execution function reads the compiled tape from the bind data and allocates the primal and adjoint buffers once. It then replays the tape for each row in the chunk, writing the resulting gradients into the output vector. Allocating the working buffers per chunk rather than per row avoids repeated memory allocation in the evaluation loop.

This design allowed the implementation to integrate naturally with the existing execution pipeline while avoiding major changes to DuckDB internals. It should be noted that the tape itself is replayed one row at a time; the AD operations are not vectorized across the chunk. The performance implications of this are discussed in Chapter~\ref{ch:conclusion}.

\section{Implementation Challenges}

Several implementation issues were encountered during development.

\subsection{Duplicate Symbol Errors}

During compilation, the forward-mode and reverse-mode implementations initially used identical internal structure and function names. Because DuckDB uses unity builds, which concatenate multiple source files into a single translation unit, this caused duplicate-definition errors such as:

\begin{lstlisting}
redefinition of 'struct AutoDiffGradBindData'
redefinition of 'struct RowInput'
\end{lstlisting}

The issue was resolved by giving the reverse-mode implementation distinct internal structure names and registration functions, separate from those used in the forward-mode implementation.

\section{Summary}

This chapter described the implementation of automatic differentiation inside DuckDB using higher-order SQL lambda functions. Forward-mode AD was implemented through dual-number propagation, while reverse-mode AD was implemented as an instruction tape compiled once at bind time and replayed during vectorized execution. Both modes return the full gradient in a single call and were integrated into DuckDB's scalar function framework, reusing the existing parser, binder, and execution engine.

Several implementation challenges were addressed during development, including lambda parameter binding, function registration conflicts, and duplicate-symbol errors arising from unity builds. The final implementation successfully supported automatic gradient computation directly inside SQL queries.

\section{Benchmark Workload}

The benchmark uses linear regression with squared loss. Synthetic datasets
were generated directly inside DuckDB using random floating-point values.

The benchmark computes the following loss function:

\begin{equation}
L = (\mathit{prediction} - y)^2
\end{equation}

where:

\begin{equation}
\mathit{prediction} = a_1x_1 + a_2x_2 + a_3x_3 + a_4x_4 + a_5x_5 + a_6x_6 + b
\end{equation}

The workload uses six input features, six trainable weights, and a single bias
parameter, giving 14 lambda parameters in total, with squared loss and twenty
gradient-descent iterations. Dataset sizes of 1{,}000, 5{,}000, 10{,}000,
20{,}000, and 50{,}000 tuples were evaluated. Each configuration was executed
five times and the median runtime is reported.

\section{Compared Methods}

Three implementations were evaluated.

\subsection{Handwritten SQL Baseline}

The baseline implementation manually computes the analytical gradients directly
in SQL using handwritten arithmetic expressions. No automatic differentiation
machinery is involved during execution.

Forward-mode AD propagates derivatives during expression evaluation using dual
numbers. The final implementation uses a flat instruction tape compiled at bind
time, CSE, tiled vectorisation, and LLVM JIT compilation. The function is

Reverse-mode AD uses a compiled instruction tape with forward and backward
passes. The final implementation applies CSE, tiled vectorisation, and LLVM
JIT compilation of both passes as a single native function. The function is
exposed as \texttt{mygrad\_rev}.

\section{CSE Effect on Tape Size}

Common subexpression elimination reduced the instruction tape from 41 to 21
operations for the benchmark expression. This halved the work in both the
forward and backward passes of reverse-mode AD, and similarly reduced the
forward-mode tape, contributing to the performance improvements seen before
JIT was applied.

\section{Analysis of Results}

The results show a clear progression: each optimization stage eliminated a
specific source of overhead.

\textbf{Bind-time operator caching} removed per-row string-based dispatch in
forward mode, reducing its overhead from $16.3\times$ to $12.7\times$ at
50{,}000 tuples.

\textbf{Flat tape compilation and CSE} eliminated recursive tree traversal
and redundant subexpression computation, reducing forward-mode overhead to
$4.4\times$ and maintaining reverse-mode at $1.25\times$.

\textbf{Tiled vectorisation} improved cache utilization by processing rows
in 256-row batches, reducing forward-mode overhead further to $2.44\times$.

\textbf{LLVM JIT compilation} eliminated all remaining interpreter overhead
by compiling the tape to native machine code at bind time. Both AD modes
reached $1.00\times$ overhead at 50{,}000 tuples, matching the handwritten
SQL baseline.

The convergence of forward-mode and reverse-mode AD to the same performance
level after JIT is explained by the structure of the generated native code:
LLVM optimises the unrolled tape operations to nearly identical machine
instructions for both modes, as reported by Schüle et al.~\cite{schule2022llvm}
for the Umbra database system.

\section{Numerical Correctness Verification}

To verify correctness, gradients produced by AD were compared against
manually derived analytical gradients. For every tuple in a 10{,}000-tuple
dataset, all seven gradients produced by both forward-mode and reverse-mode
AD were compared against the corresponding analytical gradients. The maximum
absolute difference across all tuples and all parameters was exactly zero for
both AD modes, confirming numerical correctness for the evaluated workload.

\section{Comparison with Related Work}

Schüle et al.~\cite{schule2022llvm} integrated AD into the Umbra database
system using LLVM code generation via MLIR, reporting that JIT-optimised
forward-mode and reverse-mode AD produce nearly identical machine code and
achieve equivalent runtime. This thesis replicates that finding independently
in DuckDB using a simpler flat tape intermediate representation compiled
directly to LLVM IR, without requiring MLIR infrastructure. The result
confirms that bind-time native code generation is an effective strategy for
eliminating AD overhead in relational database engines across different
system architectures.

\section{Summary}

This chapter evaluated the automatic differentiation framework across all
optimization stages. The results demonstrate that:

\begin{itemize}
    \item Each optimization stage eliminated a specific source of overhead.
    \item LLVM JIT compilation was the decisive final optimization, reducing
          both forward-mode and reverse-mode AD to $1.00\times$ overhead at
          50{,}000 tuples.
    \item Both AD modes match the handwritten SQL baseline at large dataset
          sizes, confirming that differentiable computation can be expressed
          and executed inside SQL queries with zero measurable overhead.
    \item The convergence of forward-mode and reverse-mode performance after
          JIT is consistent with findings reported for the Umbra database
          system by Schüle et al.~\cite{schule2022llvm}.
\end{itemize}

\chapter{Conclusion and Future Work}
\label{ch:conclusion}

\section{Overview}
This thesis investigated the integration of automatic differentiation into
DuckDB using higher-order SQL lambda expressions, implementing both
forward-mode and reverse-mode AD and optimizing both to match a handwritten
SQL baseline.

\section{Summary of Contributions}

This thesis integrated automatic differentiation directly into DuckDB's
query execution pipeline, using higher-order SQL lambda expressions as the
representation of differentiable programs. Both forward-mode and
reverse-mode AD were implemented and optimized through a sequence of
concrete stages --- bind-time operator resolution, flat instruction tape
compilation, common subexpression elimination, tiled vectorisation, and
LLVM JIT compilation --- bringing both modes to \(1.00\times\) overhead
relative to a handwritten SQL baseline at 50{,}000 tuples. The
implementation was further extended to support stored lambda expressions
as first-class typed values in table columns, with both a bind-time
(constant) execution path and a fully dynamic per-row execution path. The
work demonstrates that differentiable computation can be expressed and
executed natively inside a relational database engine without sacrificing
performance.

\section{Answers to Research Questions}

\textbf{RQ1 (lambda expressions as differentiable programs):} Yes — the
lambda body is extracted at bind time and compiled into an instruction tape
used for gradient computation.

\textbf{RQ2 (integration into the execution pipeline):} Both modes integrate
through DuckDB's scalar function framework. Forward mode carries dual values
through a flat tape; reverse mode runs a forward pass followed by adjoint
propagation over a compiled tape. After LLVM JIT, both execute as direct
native calls with no interpreter overhead.

\textbf{RQ3 (bind-time tape compilation and reuse):} Yes — compiling the tape
once at bind time and reusing it across all rows and gradient-descent
iterations was the single largest optimization, and CSE further reduced the
benchmark tape from 41 to 21 operations.

\textbf{RQ4 (performance overhead):} After all optimizations, both AD modes
reach 1.00$\times$ overhead relative to the handwritten baseline at 50{,}000
tuples, down from 16.3$\times$ (forward) and 2.7$\times$ (reverse) initially.

\textbf{RQ5 (vectorized execution support):} Yes — the implementation
integrates with DuckDB's chunk-based execution without major engine changes;
tiled vectorisation and LLVM JIT together bring per-row gradient computation
to native speed.

\section{Limitations}

The evaluation is restricted to a single workload --- linear regression
with squared loss --- and a fixed operator set (addition, subtraction,
multiplication, division, negation, and power); loss functions requiring
\texttt{log}, \texttt{exp}, or \texttt{max} are not currently supported.
The benefit of bind-time tape compilation and reuse is argued from the
structure of the query pipeline rather than measured directly against a
per-row-rebuild variant, since no earlier unoptimized version of the tape
compiler was preserved for comparison. The dynamic (per-row) execution
path for stored lambdas does not benefit from tiled vectorisation or LLVM
JIT compilation, since compiling native code per row would cost more than
the row itself; Table~\ref{tab:stored_lambda_bench} quantifies this gap
(a $2.03\times$ overhead relative to the bind-time path). All benchmarks were run
single-threaded, so the effect of DuckDB's native multi-threaded execution
on the AD operators remains unstudied.

\section{Future Work}
The following directions would extend this work: supporting additional
operators (logarithms, trigonometric functions); differentiating through
aggregation and window functions; SIMD-vectorizing the tape interpreter
across rows; parallelizing across DuckDB's multi-threaded execution;
replacing the flat tape with an MLIR dialect for richer optimization passes;
JIT-compiling the dynamic stored-lambda path per distinct lambda text
(rather than per row) to close its $2.03\times$ overhead against the
bind-time path while retaining full per-row flexibility; and evaluating on
workloads beyond linear regression, such as logistic regression.

\section{Final Remarks}
Embedding automatic differentiation inside SQL closes a gap between
relational analytics and gradient-based machine learning that has
typically required moving data out of the database entirely. By treating
lambda expressions as differentiable programs and compiling them to
native code at bind time, this thesis shows that gradient computation can
be made a native, zero-overhead capability of a modern analytical
database rather than an external add-on.

\chapter{Additional Implementation Details}
\label{app:implementation}

This appendix provides additional technical details regarding the
implementation of automatic differentiation inside DuckDB. The material
supplements the implementation discussion in Chapter~\ref{ch:implementation}.

\section{Complete Forward-Mode AD Implementation}

The forward-mode AD system uses dual-number propagation. Each scalar value
is extended with a gradient vector propagated through arithmetic operations
during expression evaluation.

The core structure is:

\begin{lstlisting}[language=C++]
struct Dual {
    double val;
    double grad[MYGRAD_MAX_PARAMS]; // stack-allocated, max 32 params
    idx_t  n;                       // actual number of parameters
};
\end{lstlisting}

The gradient array is stack-allocated with a fixed maximum size to avoid
heap allocation per row. The multiplication operator propagates derivatives
according to the product rule:

\begin{equation}
(a \cdot b)' = a'b + ab'
\end{equation}

\begin{lstlisting}[language=C++]
static Dual Mul(const Dual &a, const Dual &b) {
    Dual o;
    o.val = a.val * b.val;
    o.n   = a.n;
    for (idx_t i = 0; i < a.n; i++) {
        o.grad[i] = a.grad[i] * b.val
                  + b.grad[i] * a.val;
    }
    return o;
}
\end{lstlisting}

Additional operator overloads were implemented for addition, subtraction,
division, unary negation, and power.

\section{Flat Tape Compilation for Forward Mode}

The forward-mode flat tape uses the following operation structure:

\begin{lstlisting}[language=C++]
enum class FwdOpKind : uint8_t {
    INPUT, CONST, ADD, SUB, MUL, DIV, NEG, POW
};

struct FwdOp {
    FwdOpKind op;
    int32_t   a = -1;           // left operand index
    int32_t   b = -1;           // right operand index
    int32_t   input_slot = -1;  // INPUT only
    double    cval = 0.0;       // CONST only
};
\end{lstlisting}

At bind time, the expression tree is compiled to a flat vector of
\texttt{FwdOp} structures. CSE is applied to deduplicate identical nodes.
At runtime, the tape is evaluated linearly carrying a \texttt{Dual} value
per node.

\section{Reverse-Mode Tape Structure}

The reverse-mode tape uses the same structural approach:

\begin{lstlisting}[language=C++]
enum class OpKind : uint8_t {
    INPUT, CONST, ADD, SUB, MUL, DIV, NEG, POW
};

struct CompiledOp {
    OpKind  op;
    int32_t a = -1;           // left operand index
    int32_t b = -1;           // right operand index
    int32_t input_slot = -1;  // INPUT only
    double  cval = 0.0;       // CONST only
};
\end{lstlisting}

Primal values and adjoint values are stored in separate working buffers
allocated once per data chunk and reused for every row. The tape is
executed in two stages: a forward pass evaluating operations in order,
and a backward pass traversing operations in reverse to accumulate adjoints.

\section{CSE Algorithm}

The CSE pass assigns a canonical string key to each compiled operation:

\begin{lstlisting}[language=C++]
auto make_key = [&](const CompiledOp &op,
                    int32_t ra,
                    int32_t rb) -> std::string {
    char buf[64];
    snprintf(buf, sizeof(buf), "%d:%d:%d:%d:%.17g",
             (int)op.op, ra, rb,
             op.input_slot, op.cval);
    return std::string(buf);
};
\end{lstlisting}

Operations with identical keys are merged. All references to the duplicate
are redirected to the canonical node. For the benchmark expression
\texttt{(expr)*(expr)}, CSE reduced the tape from 41 to 21 operations.

\section{Tiled Vectorisation Layout}

The tiled vectorisation uses a 2D buffer layout:
\texttt{vals[op\_index * TILE + row\_index]}. This places all row values
for a single operation contiguously in memory, improving cache utilization
when the inner loop iterates over rows for a fixed operation:

\begin{lstlisting}[language=C++]
// Forward pass: operation-outer, row-inner
for (idx_t i = 0; i < prog.size(); i++) {
    for (idx_t r = 0; r < tile_count; r++) {
        vals[i * TILE + r] = ...; // all rows for op i
    }
}
// Backward pass: reverse operation order, row-inner
for (idx_t ii = prog.size(); ii > 0; ii--) {
    idx_t i = ii - 1;
    for (idx_t r = 0; r < tile_count; r++) {
        adj[(idx_t)op.a * TILE + r] += ...; // accumulate adjoint
    }
}
\end{lstlisting}

\section{LLVM JIT Bridge Architecture}

The JIT implementation uses a bridge pattern to avoid namespace conflicts
between DuckDB and LLVM:

\begin{lstlisting}[language=C++]
// In autodiff_grad.cpp (inside namespace duckdb):
#ifdef DUCKDB_HAVE_LLVM
using JitFuncType = void(*)(const double*, double*);
extern JitFuncType CompileJITBridge(
    const void* prog_ptr,
    int32_t     root,
    uint64_t    N);
#endif

// At bind time:
bind_data->jit_func = (void*)CompileJITBridge(
    (const void*)&bind_data->prog,
    bind_data->root,
    (uint64_t)n_params);

// At runtime per row:
if (bind.jit_func) {
    auto fn = (JitFuncType)bind.jit_func;
    fn(inputs.data(), grads.data());
}
\end{lstlisting}

\begin{lstlisting}[language=C++]
// In autodiff_jit.cpp (outside namespace duckdb):
JitFuncType CompileJITBridge(
    const void* prog_ptr,
    int32_t     root,
    uint64_t    N) {
    const auto* prog =
        static_cast<const std::vector<FwdOp_jit>*>(prog_ptr);
    return CompileJITImpl(*prog, root, N);
}
\end{lstlisting}

\section{Tape Compilation Algorithm}

The following pseudocode illustrates bind-time tape compilation. Each
call appends one operation and returns its index:

\begin{lstlisting}[numbers=none]
function CompileTape(expr):
    if expr is constant:
        return EmitConst(expr.value)
    if expr is variable:
        return EmitInput(expr.slot)
    if expr is unary negation:
        a = CompileTape(expr.child)
        return EmitNeg(a)
    left  = CompileTape(expr.left)
    right = CompileTape(expr.right)
    return EmitBin(expr.op, left, right)
\end{lstlisting}

After compilation, CSE is applied and LLVM JIT compiles the result
to native machine code.

\section{Effect of Tape Reuse}

A straightforward implementation of reverse-mode AD rebuilds the
computation graph for every processed tuple, placing graph construction
on the per-row execution path. The implemented design compiles the tape
once during binding and reuses it across all rows.

For a workload of $N$ rows and $I$ gradient-descent iterations, this
reduces tape construction from $N \cdot I$ times to once. For the
benchmark with $N=50{,}000$ and $I=20$, this eliminates 1{,}000{,}000
tape construction operations per benchmark run.

\chapter{Mathematical Foundations}
\label{app:proofs}

\section{Correctness of Forward-Mode AD}

Forward-mode AD propagates derivatives using the chain rule. For a
composition $f(x) = g(h(x))$, the derivative is:

\begin{equation}
f'(x) = g'(h(x)) \cdot h'(x)
\end{equation}

The implemented dual-number propagation preserves this property for
every primitive operator. For multiplication $f(x) = u(x) \cdot v(x)$:

\begin{equation}
f'(x) = u'(x) \cdot v(x) + u(x) \cdot v'(x)
\end{equation}

For division $f(x) = u(x) / v(x)$:

\begin{equation}
f'(x) = \frac{u'(x) \cdot v(x) - u(x) \cdot v'(x)}{v(x)^2}
\end{equation}

For power $f(x) = u(x)^c$ where $c$ is constant:

\begin{equation}
f'(x) = c \cdot u(x)^{c-1} \cdot u'(x)
\end{equation}

\section{Correctness of Reverse-Mode AD}

Reverse-mode AD propagates adjoint values $\bar{v}_i =
\frac{\partial L}{\partial v_i}$ backwards through the tape. For
each operation the adjoint update follows from the chain rule.

For addition $v_i = v_j + v_k$:
\begin{equation}
\bar{v}_j \mathrel{+}= \bar{v}_i, \quad \bar{v}_k \mathrel{+}= \bar{v}_i
\end{equation}

For multiplication $v_i = v_j \cdot v_k$:
\begin{equation}
\bar{v}_j \mathrel{+}= \bar{v}_i \cdot v_k, \quad
\bar{v}_k \mathrel{+}= \bar{v}_i \cdot v_j
\end{equation}

For division $v_i = v_j / v_k$:
\begin{equation}
\bar{v}_j \mathrel{+}= \bar{v}_i / v_k, \quad
\bar{v}_k \mathrel{+}= -\bar{v}_i \cdot v_j / v_k^2
\end{equation}

For power $v_i = v_j^{v_k}$:
\begin{equation}
\bar{v}_j \mathrel{+}= \bar{v}_i \cdot v_k \cdot v_j^{v_k - 1}
\end{equation}

These rules are implemented in both the tiled tape interpreter and
the LLVM JIT backward pass.

\section{Complexity Analysis}

Let $n$ denote the number of operations in the compiled tape after
CSE, and $p$ the number of parameters.

\textbf{Forward-mode AD} carries a gradient vector of length $p$
through each of the $n$ operations:
\begin{equation}
T_{\text{fwd}} = O(n \cdot p)
\end{equation}

\textbf{Reverse-mode AD} executes one forward pass and one backward
pass, each linear in $n$, independent of $p$:
\begin{equation}
T_{\text{rev}} = O(n)
\end{equation}

Memory complexity for reverse-mode AD is $O(n)$ per row for storing
primal values and adjoints. In the tiled implementation, these buffers
are allocated once per tile and reused across rows.

After LLVM JIT compilation, both modes execute at native speed with
no interpreter overhead. The asymptotic complexity remains the same,
but the constant factor is reduced to that of direct arithmetic
instructions, matching the handwritten SQL baseline.

These complexity characteristics explain why reverse-mode AD
outperforms forward-mode AD for workloads with many parameters
($p = 14$ in the benchmark), and they are consistent with the
experimental results in Chapter~\ref{ch:evaluation} and with the
standard analysis given by Griewank and Walther~\cite{griewank2008evaluating}
and Baydin et al.~\cite{baydin2017automatic}.

\section{Self-Referential Node Correction in JIT}

When CSE merges both operands of a binary operation to the same
tape node (as occurs in \texttt{(expr)*(expr)}), the backward pass
must accumulate both gradient contributions before storing. In the
JIT implementation, this requires special handling:

For $v_i = v_j \cdot v_j$ (where both operands are the same node):
\begin{equation}
\bar{v}_j \mathrel{+}= \bar{v}_i \cdot v_j + \bar{v}_i \cdot v_j
         = 2 \cdot \bar{v}_i \cdot v_j
\end{equation}

This is implemented as a single atomic accumulation to avoid the
load-modify-store race that would occur with two separate updates
to the same adjoint location.
